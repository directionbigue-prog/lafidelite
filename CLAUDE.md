## What this project is

**Cœur Fidèle — a two-player couple game, shipped as a single Next.js 16 app.** App Router Route Handlers + Server Actions + Prisma 5 + Neon + Upstash + Cloudinary + Resend + PayTech/Bictorys + Sentry, all at the repository root. There is no separate Express backend anymore — server logic lives under `src/app/api/*` and `src/lib/server/*`.

The product is two things sharing one account and one device:

1. **Le jeu du couple** (`/jeu`, `/api/games/*`) — the core loop. Two partners pair into an *Espace Couple*, then play a **pass-and-play** session of 3 rounds (Miroir, Scénario, Face-à-Face) that ends in an immutable `GameResult` and a complicity level.
2. **Le Salon** (`/salon`, `/api/salon/*`) — five light board games on the same shared device, deliberately sealed off from the couple's score.

**72 API routes; 2470 unit tests across 209 files, all green** (counted 2026-10-13, after the Salon opened to partnerless accounts). Under heavy machine load a few bcrypt-bound auth tests can time out; re-run with `--maxWorkers=3` before suspecting a regression. The UI is shipped and opinionated (see *Design system* below), and it is in French.

Origin: bootstrapped from the `izikit` starter (itself ported from `amadou-template` on 2026-05-07 through 7 phases: auth → OAuth/notifs → admin → uploads/withdrawals → webhooks/cron → docs/tests → final pass). The starter's generic surface — auth, payments, admin back-office, webhooks, cron, uploads, withdrawals — is still live and still load-bearing; the couple game sits on top of it.

**For an AI agent picking up this repo:** the architecture sections below describe what's already been built. Anything not listed under "Files Claude must NOT modify" is fair game to extend or refactor. The protected list is the small set of files where the invariants are subtle (refresh-token races, HMAC integrity, advisory locks…).

Read [README.md](README.md) for the public-facing contract (quickstart, env vars, the tiers, deploy) — it describes Cœur Fidèle as of 2026-09-22. [STATUS.md](STATUS.md) is **archaeology, not status**: it logs the starter's port and stops where the product begins. It is kept unrewritten because it explains *why* the inherited layer is shaped as it is; never answer "where is the project at?" from it. Design canvases and per-game specs live under [docs/](docs/): [docs/design/](docs/design/) (web + mobile planches), [docs/superpowers/specs/](docs/superpowers/specs/) (one spec per game), [docs/superpowers/plans/](docs/superpowers/plans/).

## High-level architecture

**Single Next.js 16 App Router app at the repository root.** One `package.json`, no workspace, no nesting — `src/`, `prisma/`, `public/`, `scripts/` and the Next config all sit beside it. There is no `backend/` package and no `` package: all server code is colocated under `src/`. The layout is deliberately flat because Vercel's framework detection reads the package manifest at the project's Root Directory, and anything else reintroduces the failure documented under *Critical invariants*.

**Boot flow** — Next.js owns the server lifecycle, so there is no hand-rolled middleware chain. Three things matter:
1. **`instrumentation.ts`** is Next's `register()` hook — Sentry inits here (server + edge via `sentry.{server,edge}.config.ts`; client via `sentry.client.config.ts`). No DSN env → silent no-op.
2. **Every Route Handler MUST `export const runtime = 'nodejs'`** (Prisma + bcrypt + raw-body needs). [src/lib/server/observability/runtime-enforcement.test.ts](src/lib/server/observability/runtime-enforcement.test.ts) walks `app/api/**/route.ts` and fails CI if any route forgets it.
3. **Per-request observability** flows through [src/lib/server/observability/request-context.ts](src/lib/server/observability/request-context.ts) (`makeRequestContext` + `withRequestContext` + scoped `log`). Handlers wrap their body in `withRequestContext()` so logs auto-attach `requestId` / `userId` / `route`.

**Optional providers boot conditionally.** If `CLOUDINARY_*` / `RESEND_*` / `BICTORYS_*` / `GOOGLE_*` envs are absent, the corresponding routes either 404 silently or return 503 (e.g., `/api/upload` → 503 STORAGE_NOT_CONFIGURED when Cloudinary creds are missing). `src/lib/server/redis.ts` exposes `redis: Redis | null` (returns `null` rather than throwing when env is missing — call sites decide fallback). The app still boots and `/api/auth` still works. `log.warn` announces which providers are inert.

**Auth model** ([src/lib/server/auth.ts](src/lib/server/auth.ts)): access JWT (15min, all paths) + refresh JWT (7d, scoped to `/api/auth` for blast-radius reduction) + CSRF token (7d, double-submit cookie). All cookies are namespaced by `COOKIE_PREFIX` (default `app`) and set via `cookies()` from `next/headers` (async). All mutating endpoints require the `x-csrf-token` header echoed from the `<prefix>-csrf` cookie — `verifyCsrf(req)` returns a `NextResponse | null` you bail on at the top of each handler. **Signup is enumeration-resistant**: identical 201 response regardless of email existence, no cookies issued at signup — cookies are issued by `POST /verify-email` after the user enters their 8-char Crockford code. Per-email rate limits (login 10/15m, signup 5/h, etc.) sit on top of the global IP limiter via [src/lib/server/middleware/rate-limit-by-email.ts](src/lib/server/middleware/rate-limit-by-email.ts).

**Middleware HOFs** ([src/lib/server/middleware/index.ts](src/lib/server/middleware/index.ts)) — `requireAuth` / `requireAdmin` / `requireSuperadmin` / `requireOrgRole` / `optionalAuth` each return `Context | NextResponse`. Pattern in handlers: `if (auth instanceof NextResponse) return auth;`.

**Frontend `api()` wrapper** ([src/lib/api.ts](src/lib/api.ts)): auto-refreshes on 401 with a single-flight lock, attaches CSRF, and **only retries `GET`/`HEAD` on network errors** — never mutating verbs (would risk duplicate charges/withdrawals). `ApiError.code` exposes the server's stable error code (e.g. `PIN_REQUIRED`, `INSUFFICIENT_BALANCE`) — switch on `.code`, not on `.message`.

**Webhook idempotency + outbox:** [src/lib/server/webhook/handler.ts](src/lib/server/webhook/handler.ts) returns `(NextRequest) => Promise<NextResponse>` and reads the raw body via `await req.arrayBuffer()` (preserves byte-identical HMAC). The handler runs a `Serializable` Prisma transaction with `WebhookLog @@unique([externalId, eventType])` for dedup. Side-effects (emails, notifications) must NOT run as a postCommit closure — they go to the **outbox** ([src/lib/server/outbox/](src/lib/server/outbox/)) inside the same tx, drained by a Vercel Cron route ([src/app/api/cron/outbox-drain/route.ts](src/app/api/cron/outbox-drain/route.ts), every 1 min).

**Withdrawals are race-free:** the route runs guards + PENDING insert inside a `Serializable` Prisma transaction guarded by `pg_advisory_xact_lock(hashtext(userId))` ([src/lib/server/withdrawals/lock.ts](src/lib/server/withdrawals/lock.ts)). Two concurrent attempts for the same user serialize on the lock, so the second one sees the first's PENDING reservation and is correctly rejected as `INSUFFICIENT_BALANCE`.

**Payments are pluggable** behind the `PaymentProvider` interface ([src/lib/server/payments/](src/lib/server/payments/)). Bictorys is the default. A single in-memory `CircuitBreaker` guards charge calls. Webhook replay window defaults to 60s (`BICTORYS_WEBHOOK_REPLAY_WINDOW_MS` to override).

**Cron strategy.** No `setInterval` loops — Next.js / Vercel doesn't keep long-lived processes. Background work runs as scheduled routes under `app/api/cron/<name>/route.ts`, each gated by `Authorization: Bearer ${CRON_SECRET}`, and invoked by the host (`netlify.toml` + `netlify/functions/` since 2026-10-03, `vercel.json` before that). Seven targets: `outbox-drain`, `email-queue-drain`, `verification-cleanup`, `order-expiration`, `webhook-log-purge`, `email-job-purge` (purges SENT EmailJob rows older than `EMAIL_JOB_RETENTION_DAYS`, default 30), and `rappels-couple` (added 2026-10-13, daily at 18:00 UTC — see *Le rituel* below). The *frequencies* are a property of the host, not of the job — read them from the two config files rather than from here, because the Hobby cap flattened all six to daily on Vercel while Netlify runs the two drains every ten minutes. Multi-instance coordination still uses [src/lib/server/leader-lease.ts](src/lib/server/leader-lease.ts) Redis leases where two crons could collide. The Bictorys charge `CircuitBreaker` is still in-memory single-instance — replace with a Redis-backed variant for multi-pod prod (documented limitation).

**Google OAuth (Sign in with Google)** — [src/lib/server/oauth/google.ts](src/lib/server/oauth/google.ts) + Phase 2 route handlers under `src/app/api/auth/oauth/google/{start,callback}/route.ts`. Implemented with `arctic` (OAuth 2.0 + PKCE). `start` issues state + PKCE-verifier cookies (5min, path-scoped to `/api/auth/oauth`) and 302s to Google. `callback` validates state, exchanges code, decodes ID token, refuses unverified emails, find-or-create user with account linking by email, then issues our standard auth cookies. Frontend errors land on `/auth/error?code=…` (see [examples/frontend-pages/auth-error.tsx](examples/frontend-pages/auth-error.tsx)). Inert without `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_REDIRECT_URI`.

**Multi-tenancy is opt-in.** [src/lib/server/middleware/require-org-role.ts](src/lib/server/middleware/require-org-role.ts) ships role types + rank helpers (`OWNER` > `ADMIN` > `MEMBER`). Default project surface stays user-owned (`Order.userId`, `Withdrawal.userId`). Apps that need orgs add `organizationId String?` on their domain models case by case and gate routes via `requireOrgRole('ADMIN', 'orgId')` from the middleware HOFs. Owner promotion is transactional (3 ops in a single tx). Non-members get **404, not 403**, to avoid leaking org existence.

**Admin back-office** — [src/lib/server/admin/audit.ts](src/lib/server/admin/audit.ts) + [src/lib/server/middleware/require-admin.ts](src/lib/server/middleware/require-admin.ts). App-wide role on `User` (`USER` < `ADMIN` < `SUPERADMIN`). Phase-5 endpoints under `/api/admin/*` cover users (search/detail/role-change), orders (filter), withdrawals (filter + manual cancel), audit-log (paginated/filterable), and `/me` (admin probe). Every mutation calls `logAdminAction(prisma, {...})` → `AdminAction` row so we can answer "who did what when" during incidents. Bootstrap the first SUPERADMIN with `pnpm db:make-superadmin <email>` (the script lives at [scripts/make-superadmin.ts](scripts/make-superadmin.ts)).

**`/admin/tableau-de-bord`** (added 2026-10-13) is the SUPERADMIN overview: accounts, couples, games, ritual, Salon, sales by pack, email/outbox health and alerts, refreshed every minute. Its route `GET /api/admin/tableau-de-bord` is read-only and gated by `requireAdmin('SUPERADMIN')`; the aggregation lives in [lib/admin/tableau-de-bord.ts](src/lib/admin/tableau-de-bord.ts) and the screen in `components/admin/TableauDeBord.tsx` (a `components/admin` file, so `surfaces-cablees.test.ts` sees the call). It adds no capability to `/api/admin/me`, whose list is contractual.

The twelve routes shipped with **no screen at all** until 2026-10-02; `/admin` ([src/app/admin/page.tsx](src/app/admin/page.tsx)) is that screen, and it adds no rules of its own. Two things about it are load-bearing. First, it **protects nothing**: hiding the role selector from an ADMIN stops no one from calling the API, and the real gate is `requireSuperadmin` inside the route — what the page hides, it hides to avoid offering an action that would come back 403, which is ergonomics, not security. Never move a check out of a route and into this page. Second, every decision it makes lives in [src/lib/admin/console.ts](src/lib/admin/console.ts) rather than in the component, because there is no jsdom here and a component cannot be mounted; the page is a thin wrapper over a module with 22 tests. The one rule the console adds beyond the API's is a confirmation before a SUPERADMIN demotes **themselves** — the server only refuses the *last* SUPERADMIN, so demoting yourself while another exists is allowed, succeeds, and locks you out of the console with only `pnpm db:make-superadmin` to get back in.

**Le jeu du couple — pass-and-play, and why the server is the only referee.** The core loop lives in [src/lib/server/game/](src/lib/server/game/) (server decisions), [src/lib/game/](src/lib/game/) (pure screen logic), and `/api/games/*`. Unlike the Salon, this engine runs **server-side**: a Scénario option carries a hidden weight and each partner's answer must stay secret until the reveal, so there is genuinely something to protect.

- **Pairing (Espace Couple).** `Couple` goes `PENDING` → `ACTIVE` when the partner joins with the 6-digit invite code (7-day TTL, [couples/invite-code.ts](src/lib/server/couples/invite-code.ts)). A user belongs to **at most one** PENDING/ACTIVE couple. Two lookups exist and are not interchangeable: `findActiveCoupleForUser` (PENDING|ACTIVE — for the pairing flow) and `findActivatedCoupleForUser` (ACTIVE only — for the game engine, because a couple with no partner yet must not be able to start a session). Both live in [couples/queries.ts](src/lib/server/couples/queries.ts).
- **Session shape.** `GameSession` → 3 `GameRound` (MIROIR, SCENARIO, FACEAFACE) → N `GameRoundQuestion`. The questions are **drawn and locked in at session-create time** ([question-selection.ts](src/lib/server/game/question-selection.ts)) so resuming after a closed tab never re-draws a different question. Anti-repetition is per couple via `QuestionUsage`: a category is "exhausted" once the couple has played ≥80% of it, and an exhausted category becomes fully eligible again rather than blocking the round.
- **The pass-and-play auth model — read this before touching `/api/games/*`.** Both partners share **one** authenticated device, so `Answer.userId` is `Couple.creatorId` or `Couple.partnerId` and is deliberately **not** `auth.user.sub`. The turn boundary is `GameSession.activePlayerRole`, a state-machine field — not a second auth check. "Hardening" this into a per-request identity check breaks the game outright.
- **Phase machine.** [state-machine.ts](src/lib/server/game/state-machine.ts) owns `PASS_DEVICE → ANSWERING → ROUND_REVEAL → ROUND_INTRO → COMPLETE`, plus `TOTAL_ROUNDS` and `QUESTIONS_PER_ROUND`. It is authoritative: anything needing those numbers imports them rather than restating them (three unlinked copies of `5` had already drifted). Round length is now a property of the session's format ([formats.ts](src/lib/game/formats.ts): `EXPRESS` is 2/2/1, `STANDARD` 5/5/5, `LONGUE_SOIREE` longer), so callers pass it in.
- **`GameResult` is computed once and immutable** — never recomputed on read, so the score a couple sees never changes between refreshes. It is written by the final-round branch of `POST /api/games/:id/round/advance`.
- **One free game per COUPLE** (since 2026-10-13; it was per account before), claimed at first session-create on the launching account's `freeGameUsedAt`, and refused when the *partner's* account already carries a claim (`partieOfferteDejaJouee` in [free-game.ts](src/lib/server/game/free-game.ts)). After it, `/jeu/nouvelle` shows the paid packs and sends to `/tarifs`. The `FREE_GAME_EXEMPT_EMAILS` escape hatch fails **closed** (missing/empty ⇒ nobody exempt) and refuses a wildcard on purpose.
- **Several accounts per device (since 2026-10-13).** `/api/auth/comptes` keeps the *other* accounts' refresh JWTs in an httpOnly cookie `<prefix>-comptes`, path `/api/auth`, max 5 ([lib/auth/comptes-appareil.ts](src/lib/auth/comptes-appareil.ts)); the active account keeps the normal cookies from the protected `auth.ts`, which is untouched. Every switch re-verifies the stored token exactly like `/api/auth/refresh` (signature, user exists, `tokenVersion`, not SUSPENDED), so the vault grants nothing the device did not already hold — a password change still kills them all. Logout clears only the active account; the others stay switchable from `/connexion`. Surfaces: `/settings` and `/connexion` via `components/auth/ComptesAppareil.tsx`.
- **The admin console calls `apiAdmin()`, never `api()`** ([lib/admin/api-admin.ts](src/lib/admin/api-admin.ts)). `api()` does not prefix `/api` (`API_URL` is `''`), so `api('/admin/me')` fetched the *page* and got an HTML 404: the whole console was dead in production until 2026-10-13 while every route answered correctly. `api-admin.test.ts` forbids a direct `api(` in `app/admin/**` and `components/admin/**`.
- **Only the inviting partner signs up.** The invitee opens `/invite/[code]`, types a first name, and `POST /api/invites/[code]/accept` creates their account, activates the couple and issues the session cookies in one transaction — the 6-digit single-use code is the credential. The account has no password and a placeholder address in the reserved `.invalid` domain ([lib/couples/compte-invite.ts](src/lib/couples/compte-invite.ts)); `EmailQueue.enqueue` refuses those addresses, so no mail ever bounces off one. The route is public and pre-session (no CSRF cookie yet), so it refuses a cross-site `Origin` instead and is IP-rate-limited. Consequence to know: a guest who loses their cookies (logout, new phone, 7 days without opening the app) has no way back into that account.

**Le Salon — board games, and why the rules engine runs in the browser.** `/salon` hosts light two-player games played on one shared device. Five ship: **dames, awalé, ludo, le mot, mots croisés** ([lib/dames/](src/lib/dames/), [lib/awale/](src/lib/awale/), [lib/ludo/](src/lib/ludo/), [lib/mot/](src/lib/mot/), [lib/mots-croises/](src/lib/mots-croises/)), with screens under [src/app/salon/](src/app/salon/) and routes under `/api/salon`. Each rules engine is pure TypeScript executed **client-side**, and the server never validates a move. That is a decision, not an omission: these games have no hidden information, no real score, and both players share one screen, so server-side validation would protect nothing while costing a round trip per move (~320 ms floor — see [docs/notes/latence-base-de-donnees.md](docs/notes/latence-base-de-donnees.md)). The server persists the board and checks its **shape only** via each game's `parseEtat*`; anything stricter would duplicate the engine. Three invariants hold this together:

- **[lib/salon/jeux.ts](src/lib/salon/jeux.ts) is the single registry.** `JEUX`, the `estUnJeu` type guard, the initial state and the shape parser per game all live there, behind exhaustive `switch`es — so adding a sixth game is a typecheck error until every arm is filled. This file exists because the list once lived twice (`api/salon/route.ts` and `api/salon/current/route.ts`) with two divergent guards: a game could be created but never resumed, and no test said so. Extend `jeux.ts`, never the routes. Note also that a game engine never calls `Math.random()` itself — drawing (e.g. the crossword grid) is the caller's job, and `jeux.ts` is that caller.
- **`BoardGame` is generic** (`kind`, `state Json`, `moveCount`) so a sixth game needs no migration. Don't specialise it. One game in progress per couple per kind is enforced by a **partial** unique index in raw SQL (Prisma's DSL cannot express the `WHERE`), and `POST /api/salon` must catch the resulting `P2002` and return the existing game — both partners can start one in the same second.
- **The Salon needs no partner (since 2026-10-13).** A `BoardGame` belongs to the ACTIVE couple **or**, when the caller has none (no couple, or a PENDING one), to the account alone: `coupleId` is then null and `userId` carries the game. A raw-SQL `CHECK` (`BoardGame_un_seul_proprietaire`) forbids both and neither, and a second partial unique index (`BoardGame_user_kind_in_progress_unique`) keeps one game in progress per account per kind. All four `/api/salon` routes resolve the owner through [server/salon/proprietaire.ts](src/lib/server/salon/proprietaire.ts) (`proprietaireDuSalon` + `partiesDe` in every `where`) — a route still filtering on `coupleId` alone would let a solo account create a game it could neither save nor end, and `proprietaire.test.ts` fails on it. The paywall is unchanged: a solo account needs its own paid pack (`SALON_LOCKED` otherwise). Solo games stay on the account when it later pairs; they simply stop being read while the couple is active. The second player's label comes from [lib/salon/second-joueur.ts](src/lib/salon/second-joueur.ts) ("Joueur 2" without an active couple), and `/couple/creer` + `/couple/attente` link to `/salon` because those screens have no app navigation.
- **Saves are guarded by monotonic `moveCount`**: a single `updateMany` whose `where` carries id + couple + `status: 'IN_PROGRESS'` + `moveCount: { lt: next }`. Read and write stay atomic, so a save that arrives late cannot overwrite a newer board — it simply matches no row, which is the nominal stale case (409), not a server error. Never split this into a read followed by a conditional write.
- **Total sealing from the couple's game.** Nothing here may touch `cumulativeCoupleScore`, `GameResult`, or the complicity level. A Salon game is the one place in the app with a winner, and it must stay outside the couple's score.

**Le rituel — the daily reason to come back (added 2026-10-13).** `/rituel` ([lib/rituel/](src/lib/rituel/), `/api/rituel`, `/api/rituel/question-du-jour`, cron `rappels-couple`) carries four levers: a daily MIROIR question, a streak ("flamme"), badges and a milestone journal, and one gentle reminder email per absence. Rules that hold it together:

- **Streak, badges and souvenirs are DERIVED, never stored.** They are recomputed from completed `GameSession`s and `ReponseDuJour` rows on every read ([serie.ts](src/lib/rituel/serie.ts), [badges.ts](src/lib/rituel/badges.ts)). A stored streak would need a midnight cron and would lie the day it missed; a stored badge would need every write path to remember it. Do not add columns for them.
- **A day counts only when the couple did something TOGETHER**: a completed game, or BOTH partners answering the daily question. The Salon does not count — it stays sealed.
- **One grace day per 7 calendar days**; the missed day protects the streak but is not added to its length.
- **The daily question reveals nothing until both have answered, and only on that day** ([question-du-jour.ts](src/lib/rituel/question-du-jour.ts)) — the "no past answer is consultable" guardrail applies here too; the journal holds dates and titles only. The answering role comes from the body (pass-and-play), uniqueness is the `(coupleId, jour, role)` index, and the day is always the SERVER's UTC date (= Dakar time). It touches neither `cumulativeCoupleScore` nor `GameResult`.
- **Three ritual emails, one switch.** « À ton tour » (sent from `POST /api/rituel/question-du-jour` when the other partner has not answered yet, one per partner per day, never revealing the answer, never failing the request), « flamme en danger » (cron, only when a ≥2-day streak dies at midnight without play tonight) and the absence reminder below — the cron sends at most ONE of the last two per couple per evening. All three go through [rituel/notifier.ts](src/lib/server/rituel/notifier.ts) and obey the single `RAPPEL_COUPLE` preference.
- **Reminders: one per absence, 2 to 14 days, opt-out.** The dedupe key carries the last active day, so a re-run never re-sends; the notification is created first and the email enqueued only if it was new. Users switch them off in `/settings` (event `RAPPEL_COUPLE`). No email is sent — and no notification is created — while the email queue is unconfigured, so a reminder is never "consumed" unsent.

**Remote play — two phones, no video (added 2026-10-13).** Partners in two places play the same game on two phones. A video call (Daily.co) shipped with it the same day and was **removed** that evening at the product owner's request: no Daily SDK, no `/api/video`, and `Permissions-Policy` is back to `camera=(), microphone=()`. Do not reintroduce camera/microphone rights without a feature that uses them. Rules:

## Critical invariants

- **Every Route Handler MUST `export const runtime = 'nodejs'`.** The runtime-enforcement test in `src/lib/server/observability/` fails CI otherwise (Prisma + bcrypt break on edge).
- Webhook handlers read the raw body via `await req.arrayBuffer()` and hash it BEFORE any JSON parse — calling `await req.json()` first is a silent HMAC-verification regression.
- Notification dispatchers MUST go through `createNotification(prisma, input)` — never `prisma.notification.create` directly (skips the dedup `P2002` catch).
- Webhook handlers emit side-effects via the **outbox** (`enqueueOutbox(tx, event)` inside the tx) — never via fire-and-forget closures.
- Withdrawals must use the advisory-lock + Serializable tx pattern (the `withdrawals/lock.ts` helper does this — just call it). Calling guards + insert outside a tx is a double-spend regression.
- Payment amounts are **integer in smallest currency unit** (FCFA = no decimals; USD = cents). Never store decimals.
- `BICTORYS_API_KEY` (charges) and `BICTORYS_PRIVATE_KEY` (payouts) are distinct keys — must NEVER be confused.
- Withdrawal balance check is ON by default (`WITHDRAWAL_BALANCE_CHECK=0` to disable). Disabling on a real-money project is a financial-safety risk — only do it if you have an alternative ledger.
- Withdrawal guards return **stable error codes** (`AMOUNT_BELOW_MIN`, `AMOUNT_ABOVE_MAX`, `DAILY_LIMIT_EXCEEDED`, `COOLDOWN_ACTIVE`, `PIN_NOT_SET`, `PIN_REQUIRED`, `PIN_INVALID`, `INSUFFICIENT_BALANCE`). Frontend switches on `ApiError.code`, not translated messages.
- Frontend `api()` retries only `GET`/`HEAD` on network errors. Do not extend to `POST`/`PUT`/`PATCH`/`DELETE`.
- Signup never sets cookies and never reveals email existence. Cookies are issued by `/verify-email` after the user enters their code.
- **Any field taking the 8-character code cleans its input through [lib/auth/verification-code.ts](src/lib/auth/verification-code.ts) and shape-checks it BEFORE the request.** The server's regex answers a bare `VALIDATION_FAILED`, the client renders that as "Le formulaire contient une erreur.", and each refused attempt spends one of five per quarter-hour — so a leading or grouping space used to lock a user out with the right code in front of them. Never put `maxLength={8}` back on such a field: it truncates a grouped paste in the browser, before any handler can clean it. Two screens consume this: `/verify-email` and `/reinitialiser-mot-de-passe`.
- Upload route enforces magic-byte validation against `UPLOAD_ALLOWED_MIME` via [src/lib/server/upload/sniff.ts](src/lib/server/upload/sniff.ts) — don't bypass by trusting `File.type` alone.
- Admin mutations MUST go through `logAdminAction(prisma, {...})` — every back-office write is auditable. Skipping it is a compliance regression.
- Admin role precedence: `USER` < `ADMIN` < `SUPERADMIN`. Only SUPERADMIN can change roles. The route refuses to demote the **last** SUPERADMIN to avoid locking the org out.
- Org role precedence: `MEMBER` < `ADMIN` < `OWNER`. `requireOrgRole(min, paramName)` returns **404** to non-members (not 403) so org existence isn't leaked.
- OAuth callback MUST refuse `email_verified !== true` from Google — otherwise an attacker with an unverified Google account matching a victim's email can take over the account via auto-linking.
- Cron handlers MUST verify `Authorization: Bearer ${CRON_SECRET}` to prevent unauthenticated invocation of background work.
- **Every cron handler MUST export `GET`, because that is the only verb Vercel sends.** The docs are explicit: *"To trigger a cron job, Vercel makes an HTTP GET request to your project's production deployment URL, using the `path` provided in your project's vercel.json file."* All six handlers exported `POST` and nothing else, so the first successful production deployment (2026-10-02) shipped with every scheduled job dead — the scheduler collected a bare 405 six times a day. The failure writes no log line, raises no error and shows no failed invocation: a cron that is never invoked is indistinguishable from a quiet one, and two of the six carry user-facing mail. It was found only by probing the six paths from outside. Keep `POST` exported too (the drain scripts and the route tests call it, and it is the honest verb for a mutation) and alias `GET` to it; both go through `verifyCronSecret`, so neither is open. Locked by [cron-get-alias.test.ts](src/lib/server/observability/cron-get-alias.test.ts) — note that its first version matched the raw source and a commented-out `// export const GET = POST;` satisfied it, so it now strips comments before matching. `vercel-json-shape.test.ts` only proves the route *file* exists; a file existing is not a handler answering, and that gap is what shipped. Netlify does not constrain the verb — the scheduled functions there send `POST`, the honest one — so keep **both** exports: `GET` is what Vercel needs, `POST` is what everything else uses.
- **The app lives at the repository root, and that is a deployment requirement, not a preference.** Vercel's framework detection reads the `package.json` at the project's Root Directory — a dashboard-only setting that no file in this repo can carry (`rootDirectory` is not a `vercel.json` property; the documented property table has no such key). While the app sat in `` behind a one-package pnpm workspace, the root manifest was an orchestrator with no `next` in it, and a project left on the default root refused to build: *"No Next.js version detected"* — wording that names the dependency, not the cause. That failed six consecutive deployments on 2026-10-01. The repo was flattened on 2026-10-02: one `package.json` with `next` in `dependencies`, one `vercel.json` beside it, zero overrides. Do not re-nest the app, do not re-add `pnpm-workspace.yaml` for a single package, and do not "fix" a nesting by adding a second `vercel.json` — whichever copy Vercel happened to read would decide which crons got registered, depending on a setting nobody is looking at. Both halves are locked by [package-json-deployable.test.ts](src/lib/server/observability/package-json-deployable.test.ts) and [vercel-json-shape.test.ts](src/lib/server/observability/vercel-json-shape.test.ts).
- **`pnpm.overrides` in `package.json` is read by pnpm 9 and ignored by pnpm 10+.** The five overrides there are what closed 17 high-severity CVEs and turned CI green for the first time in this repo's history. pnpm 10 moved the setting to `pnpm-workspace.yaml`, so bumping `packageManager` past 9.x would silently reopen all seventeen — green lockfile, green install, no error anywhere. `packageManager: pnpm@9.15.0` is therefore load-bearing, and `package-json-deployable.test.ts` fails CI if the two ever disagree. To move to pnpm 10+, relocate the overrides first and re-run `pnpm audit --prod --audit-level=high`.
- **Every cron schedule in `vercel.json` must be legal on a Hobby account: at most once per day.** Vercel refuses to *deploy* a sub-daily expression, so nothing at runtime can catch it — [vercel-json-shape.test.ts](src/lib/server/observability/vercel-json-shape.test.ts) does, by requiring a fixed number in both the minute and hour fields. It also requires `outbox-drain` to sit in an earlier hour than `email-queue-drain`, because the first feeds the second and Hobby jitter (±59 min) never leaves the declared hour. This constraint belongs to that file alone: `netlify.toml` has no such cap, and its schedules are deliberately tighter.
- **The hosting target is Netlify since 2026-10-03, and the two cron inventories must stay in step.** `vercel.json` is read *only* by Vercel, so moving host silently unschedules all six jobs — the same shape of failure as the `POST`-only one above, and just as invisible. Netlify has no declarative equivalent: its Scheduled Functions are code. So [netlify.toml](netlify.toml) carries the six schedules and `netlify/functions/cron-<name>.mts` carries six shells that **decide nothing** — origin, secret, verb and the 30-second scheduled-execution limit all live in [lib/server/cron/appel-planifie.ts](src/lib/server/cron/appel-planifie.ts), which is pure and tested, because `netlify/` is covered by neither `eslint src/` nor tsconfig's `include`. Two rules hold it together. A shell **must not swallow its error**: an exception marks the invocation failed in the Netlify UI, and that is the only observable signal that a cron is dead — logging "ok" on a 401 is the September outage rebuilt. And the scheduled function **calls the route over HTTP** rather than redoing its work: a second path would want a second Prisma client in a second bundle, and two paths drift. [netlify-toml-shape.test.ts](src/lib/server/observability/netlify-toml-shape.test.ts) requires that the six routes, the six schedules and the six shells correspond, that each shell names *its own* route, and that `netlify.toml` and `vercel.json` cover exactly the same set — so a seventh cron cannot be added to one host only. Three further facts no code can re-derive: a Netlify variable is **scoped** (a `CRON_SECRET` scoped *Builds* only is invisible at runtime, and Vercel has no such split); `binaryTargets` must name `rhel-openssl-3.0.x` because Netlify builds on Ubuntu and runs on Amazon Linux, so a `native`-only client dies on its first query after a green build; and `.nvmrc` must name a currently-supported Lambda runtime, or Netlify silently runs the functions on Node 24 while the build used something else.
- **The interactive mail path does not wait for a cron.** A route that enqueues a user-facing email calls `scheduleDrain(ctx.requestId)` from [outbox/drain-now.ts](src/lib/server/outbox/drain-now.ts), which flushes the outbox and the email queue inside Next’s `after()` once the response is out. Daily crons alone would mean a verification code arriving up to 24 h late — a green deploy with signup silently dead. Unlike the cron routes, this path takes NO lease: two simultaneous signups must both get their mail, and both layers below already claim atomically.
- **`EmailQueue.drainOne()` returns a `DrainOutcome`, never a boolean, and a `'skipped'` must never be counted as a send.** A Redis pointer whose `EmailJob` row is gone or already terminal leaves the queue with no mail moving. As a boolean that was indistinguishable from a successful send, so `drainNow` logged `sent: 1` while the user's code sat `PENDING` — a four-day outage behind a reassuring log line. Two rules follow: a stale pointer costs **no** `BATCH` slot in the interactive path (otherwise one ghost per request starves the real mail), and every drain logs `sent` / `failed` / `skipped` together. The backlog that caused it came from deleting `EmailJob` rows whose ids were still queued — **never delete `EmailJob` rows without draining `q:email` first.** Covered by [email-queue.test.ts](src/lib/server/queues/email-queue.test.ts) and [drain-now.test.ts](src/lib/server/outbox/drain-now.test.ts).
- Cookies stay `httpOnly` + `Secure` (prod) + `SameSite=Lax`.
- Sentry init stays in [instrumentation.ts](instrumentation.ts) `register()` — do not move it into a route module (the hook fires before app code, route imports do not).

Couple-game invariants (these are the ones an agent breaks by accident):

- **Four partial unique indexes live only in raw SQL** — `Couple_creator_active_unique`, `GameSession_couple_in_progress_unique`, and the Salon's two one-game-per-kind indexes (`BoardGame_couple_kind_in_progress_unique`, `BoardGame_user_kind_in_progress_unique`) — plus the `BoardGame_un_seul_proprietaire` CHECK, because Prisma's DSL has no `@@unique … WHERE`. `prisma migrate dev` diffs the shadow DB (which has them) against `schema.prisma` (which cannot declare them) and **will generate a `DROP INDEX`**. Delete that statement from the generated migration before applying it; accepting it silently removes the "one active couple" and "one game in progress" guarantees, and nothing fails until two rows exist.
- Every `/api/games/*` response carrying a `Question` or another player's `Answer` MUST pass through [game/response-shaping.ts](src/lib/server/game/response-shaping.ts). Two non-negotiables: a SCENARIO option's `weight` never reaches a client, and the partner's answer is never visible before the round is `COMPLETED`.
- `Answer.userId` is the couple's `creatorId`/`partnerId`, **not** `auth.user.sub` — pass-and-play shares one authenticated device. The turn boundary is `GameSession.activePlayerRole`, not a second auth check.
- [game/scoring.ts](src/lib/server/game/scoring.ts) and [game/state-machine.ts](src/lib/server/game/state-machine.ts) must stay Prisma-free, `server-only`-free and isomorphic: `/demo` bundles them into the **browser** so a visitor without an account plays against the real engine. A bare `import crypto from 'node:crypto'` breaks that bundle at import time whatever code path runs — use `globalThis.crypto`.
- **Access tiers are resolved per COUPLE, not per account** ([game/entitlements.ts](src/lib/server/game/entitlements.ts)): one partner holding a pack unlocks the couple. Since 2026-10-13 `free-game.ts` also counts per couple (one free game for the two of them), though the claim is still written on the launching account. `Entitlement` rows are **additive**: a user may hold several at once, and `packEffectif` keeps the best unexpired one. There is no partial unique index here, unlike Couple/GameSession/BoardGame — overlapping ACTIVE rows are nominal.
- **A paid pack exempts from the one-free-game rule.** `POST /api/games` sets `exempt` when `pack.prix > 0`. Removing that is how a subscriber pays 9 900 FCFA and is then refused their second game.
- **The paid tiers differ by DURATION, not by content** (decided 2026-10-02): Week-end 2 000 / 2 days, Semaine 4 900 / 7 days, Mois 9 900 / 30 days, each opening the whole catalogue and the Salon. `Pack.dureeJours` replaced `dureeMois`, which could not express two days or a week, and `finDuDroit` now does millisecond arithmetic instead of `setMonth` — the calendar methods normalised impossible dates silently, so a "one month" right bought on 31 January ran to 3 March. Two consequences worth knowing before touching this: changing a duration in the registry does **not** shorten rights already sold, because `Entitlement.expiresAt` is frozen at purchase; changing the theme list **does** apply retroactively, because the registry is read at decision time — which is why widening the paid tiers to the full catalogue took nothing away from anyone.
- **A pack withdrawn from sale stays in the registry.** `ANNUEL` carries `enVente: false` rather than being deleted. `Entitlement.packId` stores the string, so removing the entry would make `packParId` return `null` for customers who paid and drop them to Découverte via `packEffectif`. Sell through `PACKS_PAYANTS` / `PACKS_VISIBLES` and check `estAchetable()` before creating an order; never iterate `PACKS` in a shop surface.
- **The admin console surfaces all twelve back-office routes, and its tabs invent no capability.** Until 2026-10-03 only `users` and `me` had a screen: orders, withdrawals, audit-log, outbox, email-queue and rate-limits answered correctly and were reachable from nowhere — a back-office you can only read with curl is not a back-office. The six tabs live in `ONGLETS` ([lib/admin/console.ts](src/lib/admin/console.ts)) and are filtered by `ongletsVisibles(can)` against the capability list `/api/admin/me` returns. **That list is contractual** — `me/route.test.ts` requires exactly 8 entries for ADMIN and 11 for SUPERADMIN — so a tab that invented a capability name would be invisible to everyone with nothing failing; [onglets.test.ts](src/lib/admin/onglets.test.ts) asserts every tab's capability exists in the contract. The same rule as the rest of this screen applies: hiding a tab protects nothing, each route re-checks. One money rule rides along: `montantLisible` never divides by 100, because amounts are integers in the smallest unit (FCFA has no decimals) and "tidying" them would show a hundredth of the real price on a financial screen.
- **The "every route has a screen" rule is now a test, because it was broken three times.** 2026-10-02: the console shipped with no link to it from anywhere. 2026-10-03, first pass: nine of twelve routes had no screen. 2026-10-03, second pass: three were still mute — including `users/[id]/status`, the only action that can close an account, and the accounts list was reading `status` out of its own response **without ever displaying it**, so a suspended account looked identical to an active one in the console that suspended it. Each time the route answered correctly, its own tests passed, and nobody could reach it. [surfaces-cablees.test.ts](src/lib/admin/surfaces-cablees.test.ts) walks `app/api/admin/**/route.ts` and requires a call for each, with `lib/admin/console.ts` counted as a surface (it builds `/admin/users`). Two things about *how* it does that. It **strips comments first, line comments before block comments** — in the other order the `/*` inside `// sous /api/admin/*` opened a block that swallowed 13 KB of the page, and a prose mention of a path satisfied the test while the real call was unplugged (verified both ways). And the one exemption, `GET users/[id]`, is held by a test of its own *reason*: the detail route's `USER_SELECT` must stay byte-identical to the list's, so the day it returns more, the exemption goes red and a screen becomes mandatory. Suspension carries the console's strongest warning, and it is not decoration: `status: 'SUSPENDED'` makes both `/api/auth/login` **and** `/api/auth/refresh` answer 403, and `scripts/make-superadmin.ts` writes only `role` — never `status` — so an admin who suspends their own account cannot be restored by any command in this repo, only by direct database access. That asymmetry with self-demotion (which `pnpm db:make-superadmin` does fix) is asserted by reading the script.
- **Every page is declared in [lib/seo/pages.ts](src/lib/seo/pages.ts), and `sitemap.ts` / `robots.ts` derive from it.** A hand-written sitemap desynchronises on the first screen added and nothing reports it — an incomplete sitemap raises no error, it just leaves pages out of the results. [referencement.test.ts](src/lib/seo/referencement.test.ts) walks `src/app/**/page.tsx` and fails CI when a page has no entry, which is the only moment anyone will think of it. Two rules the registry encodes. First, **`/invite/[code]` must never be indexable**: it carries a 6-digit pairing code valid for 7 days, so one indexed URL would let anyone join someone else's Espace Couple. Second, **a `Disallow` is not a `noindex`** — it stops the visit, not the catalogue entry, so a URL shared elsewhere can be indexed without ever being crawled. Every private segment therefore also carries `robots: { index: false }` in its own `layout.tsx` (a *layout*, because most of these screens are client components and a client component cannot export `metadata`), and the test checks each one. The root layout's `metadataBase` is equally load-bearing: without it Next renders Open Graph image URLs *relative*, no social network can resolve them, and the share card renders bare with nothing failing.
- **The brand mark is two interlocking circles with a gold intersection**, and it exists three times on purpose: [components/ui/Marque.tsx](src/components/ui/Marque.tsx) (inline, for every header — an external image would cost a request per page and arrive after layout), [public/logo.svg](public/logo.svg) (transparent, for anything outside React), and `src/app/icon.svg` (on the ink ground, because a transparent mark is invisible in a light browser tab). `marque.test.ts` asserts all three carry the same geometry — two copies of a logo that drift are two logos. The PNGs (`apple-icon.png`, `icon-192/512.png`, `opengraph-image.png`) are rasterised from the SVG and committed; regenerate them from the scripts rather than editing pixels.
- **The connection statistics store a device CLASS and a country CODE — never the IP, never the user-agent.** `ConnexionEvent` ([lib/admin/connexions.ts](src/lib/admin/connexions.ts) for the derivation, [server/admin/connexions.ts](src/lib/server/admin/connexions.ts) for the write) answers "which devices, which countries, at what rate" with two derived values and nothing else. The IP identifies a subscriber; the country derived from it barely does, and the country is all the console shows — keeping the IP "just in case" would be a risk with no use. The model has no column for it, but a column is not the guard: `pays` is a text field, so the test asserts the produced VALUE carries no address, and it bites (verified by routing `x-forwarded-for` into `pays` — four tests red). Three further rules: the write goes through `after()` and swallows every error, because a statistic must never fail a sign-in; it is wired at **login** and **verify-email** (signup issues no cookies, so a new account's first session is born at verification, not at login); and **Google sign-ins are counted through a relay, not in the callback** (since 2026-10-13): `app/api/auth/oauth/google/callback/route.ts` is protected and stays untouched, so every Google button asks for `next=/api/auth/connexion-google?next=<destination>` via `lienConnexionGoogle` ([lib/auth/lien-google.ts](src/lib/auth/lien-google.ts)); the relay records a `GOOGLE` connection only for an access token minted in the last two minutes (once per token, Redis `nx`), then redirects to a same-site path. [capture-cablee.test.ts](src/lib/server/admin/capture-cablee.test.ts) asserts the callback still records nothing itself, the relay does, and no Google link bypasses the helper. Retention is `CONNEXION_RETENTION_DAYS` (90), purged by the daily `webhook-log-purge` cron rather than a seventh schedule, since the Hobby cron quota is not reliably documented and a refused deployment would cost more than the route's slightly loose name.
- **A sales surface derives the whole card from the registry — name, price, period, theme count — not just the price.** The landing's prices had been derived since the canvas port, but the *names*, the *periods* and the theme counters were still transcribed in [app/page.tsx](src/app/page.tsx). When the paid tiers moved to duration-based pricing on 2026-10-02, the registry changed and the landing did not: production served **"Essentiel · 4 900 F · Par mois · 6 thèmes sur 8"** while the engine sold *Semaine · 4 900 · 7 days · all eight themes*, offered **"ou 118 800 F l'année"** for the `ANNUEL` withdrawn from sale the same day, and never showed the 2 000 Week-end at all. Someone paying 4 900 for what the page called a month received a week. Three further claims in the same page were false the same way: three Salon cards read "10 pts la partie" for a points currency this product has never had, one read "Gratuit" although Découverte carries `salon: false` (so the server answers `SALON_LOCKED`), and the payment footer promised points "jamais débités". All of it now comes from `pricingCards` / `salonAcces` in [landing/design-data.ts](src/lib/landing/design-data.ts). Locked by [tarifs-derives.test.ts](src/lib/landing/tarifs-derives.test.ts) — and note *how*: it compares against the registry **case-insensitively** over the page's visible text only, because a first version matched the registry's lowercase `par mois` and stayed green against the production string `Par mois, sans engagement`, and because a `>Essentiel<` match would have missed a name sitting alone on its line. Both weaknesses were found by re-injecting the exact shipped text.
- **PayTech is the live provider since 2026-10-13** (Wave, Orange Money, Free Money, card): `getProvider()` returns it as soon as `PAYTECH_API_KEY` + `PAYTECH_API_SECRET` exist, Bictorys otherwise ([payments/paytech.ts](src/lib/server/payments/paytech.ts)). Its IPN `POST /api/webhooks/paytech` goes through the protected `createWebhookHandler` via a `WebhookProvider` adapter: body form-encoded by default (JSON accepted), proof IN the body (`hmac_compute`, else `sha256` echoes of both keys — compared in constant time, stripped before WebhookLog). A pack opens only if `ref_command` is our order charged through PayTech with the same `token`, the IPN `env` equals `PAYTECH_ENV` (a sandbox payment never opens a real pack), and `item_price` matches the order. Both webhooks share [payments/encaissement.ts](src/lib/server/payments/encaissement.ts) so "mark PAID + open the pack" exists once.
- **A pack is bought through `POST /api/orders` with a `packId`, and opened by the provider webhook** (since 2026-10-13). The route reads price and currency from the registry ([lib/game/achat.ts](src/lib/game/achat.ts)) and ignores any client amount; it writes `packId` into `Order.metadata` itself and drops a client-supplied one. `onPaid` in [webhooks/bictorys/route.ts](src/app/api/webhooks/bictorys/route.ts) calls `droitDeLaCommande` and creates the `Entitlement` inside the same Serializable tx — only when the paid amount and currency equal the pack's registry price, and only once (it looks up the unique `orderId` first, because a P2002 would abort the whole tx). A refund flips that entitlement to `REFUNDED`. Amount-only orders (the starter's generic API) still work and never open anything. Bictorys returns the customer to `/paiement/[id]`, which polls `GET /api/orders/[id]` and announces the pack only once the server has actually opened it. `pnpm abonner` remains for development. The super-admin dashboard flags any paid pack order with no entitlement — that is the incident to watch.
- **A locked theme is REFUSED (403 `THEME_LOCKED`), never silently dropped.** Same reason the theme bank exists at all: a selection that is quietly ignored produces a game about something else and nobody notices. The Salon's gate (`SALON_LOCKED`) sits on **creation only** — reads, saves and `/end` stay open so an expiring pack cannot strand an unfinished board.
- **A theme is only real above 10 questions *per round type*.** The eight themes live in [game/themes.ts](src/lib/game/themes.ts) and their questions in `prisma/seed-data/themes/`. Below that threshold `narrowToCategories` **widens back to the whole round pool and says nothing** — the couple picks "Ex et passé" and plays something else. Ten is `LONGUE_SOIREE`'s per-round draw (30 = 10/10/10), so a smaller theme would work in the short format and silently lie in the long one. [themes.test.ts](src/lib/game/themes.test.ts) replays the real draw per theme per round and fails CI on `narrowed === false`.
- `GameResult` is written once and never recomputed on read. A score that changes between two refreshes is a bug, not a rounding difference.

## Design system — shipped, and enforced by tripwires

This is no longer a headless starter. There **is** a design, it is dark-on-plum with gold and wine accents, and three tests fail CI when a new screen drifts from it. Read this before writing any `.tsx`.

- **Palette and type** — [tailwind.config.ts](tailwind.config.ts): `ink`, `cream`, `gold` / `gold-deep`, `wine` / `wine-deep`, `rose`, `plum.{DEFAULT,card,card2,deep,deep2}`, plus `damier.{clair,fonce}` reserved for the Salon's board and deliberately outside the general palette. Fonts are `font-serif` / `font-grotesk` via CSS variables. Use these tokens; don't hand-write hex.
- **The UI kit** — [src/components/ui/](src/components/ui/): `Button` / `ButtonLink` / `buttonClass()`, `Alert`, `Field`, `PasswordField`, `FocusLayout`, `AmbientBackdrop`. Screen shells live in [components/app/AppShell.tsx](src/components/app/AppShell.tsx) and `components/auth/AuthSplitLayout.tsx`. Per-domain components sit under `components/{game,salon,dames,awale,ludo,mots-croises,demo,auth}/`.

Three tripwires, each written from a defect that shipped:

- **[one-button-design.test.ts](src/components/ui/one-button-design.test.ts)** — a pill-shaped CTA takes its classes from `Button`, or from `buttonClass()` where the call site must stay a raw element. The same CTA had already drifted into 32 hand-written class strings, with auth on `bg-gold` and game screens on `bg-wine`, and one "SECONDARY" byte-identical to a primary. Exempt: the landing hero in `app/page.tsx`, `Button.tsx` itself, and Google's sign-in button (brand requirements).
- **[one-layout-root.test.ts](src/components/ui/one-layout-root.test.ts)** — no page hand-writes a full-page root; only the three registered shells (`FocusLayout`, `AuthSplitLayout`, `AppShell`) may, **and each must actually be imported**. `FocusLayout` once existed with a comment about "the fourteen pages using it" and zero importers, while 22 hand-rolled `<main>` roots repeated its classes with four different gaps — so a layout fix reached none of them.
- **[app/salon/charte.test.ts](src/app/salon/charte.test.ts)** — Salon screens stay on the product's dark ground. Five games had copied a cream background from the dames screen, and `Alert` **has no light variant**: its three tones all write in `text-cream`, so every Salon error message was rendering cream-on-cream. If you put an `Alert` on a light surface, it is invisible.

**No server lib reaches into the DOM.** Routes only return `NextResponse.json(...)`, so the same API could feed a SwiftUI or Flutter client unchanged.

## Provider recommendations

When the user asks for a capability that this starter does not ship, recommend the provider listed below before falling back to a hand-rolled or in-process alternative. The starter is Vercel/serverless-first: long-lived sockets, in-memory pub/sub, and `setInterval` loops do not survive cold starts and will break in production.

| Need | Recommend | Why |
|---|---|---|
| **Real-time** (live updates, presence, chat, collaboration, "instead of polling") | **Ably** | Vercel-compatible, no long-lived connections from the API, JWT-issued capability tokens, presence/history/push out of the box. Do NOT recommend Socket.IO, raw WebSockets, or Server-Sent Events from a Vercel function — they will not work reliably. |
| Background jobs / queues | Upstash QStash, or extend the existing **outbox pattern** (`lib/server/outbox/`) drained by Vercel Cron | Same constraint — no long-running workers in a serverless runtime |
| Media / object storage | Cloudinary (already wired) | Already integrated — handles uploads, transformations, and CDN delivery |
| Email | Resend (already wired) | Already integrated |
| Cache / rate-limit / KV | Upstash Redis (already wired) | Already integrated |

**Trigger phrasing for real-time**: "live updates", "real-time", "websocket", "push notifications to the browser", "instead of polling", "chat", "presence", "collaboration", "live dashboard". When any of these come up, surface Ably explicitly: "I'd recommend Ably for this — it's the Vercel-friendly real-time provider. Want me to wire it up?" Then sketch the integration: token-mint route under `/api/realtime/token` issuing capability tokens after `requireAuth`, server-side `publish()` from route handlers via the Ably REST API, client `ably-js` subscribes to channels scoped by `userId` / `orgId`.

## Conventions

- TypeScript strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` — don't silence with `any` casts.
- ESLint 9 flat config + Prettier (run `pnpm format` before committing).
- Vitest for unit tests; setup file at [vitest.setup.ts](vitest.setup.ts), shared mocks under `src/test-utils/` (`server-only` is aliased to a no-op).
- **There is no jsdom and no Testing Library.** Vitest runs `environment: 'node'` ([vitest.config.ts](vitest.config.ts)) and neither package is installed. Components therefore cannot be mounted, and no test may `render()` anything. Two consequences, both deliberate:
  - Put a page's decision logic in a pure module and assert on it directly (`lib/game/phase-routes.ts`, `lib/game/question-screen.ts`, `lib/dames/interaction.ts` are the pattern); keep the page a thin wrapper that renders the result.
  - What genuinely lives in JSX is asserted at the source level — `readFileSync` the component and match on its text. This works, but it produces hollow tests with alarming ease: `expect(page).toContain('ApiError')` is satisfied by the import alone. Extract the block you mean (the body of one function, one JSX branch) and assert inside it, then prove the test bites by breaking the implementation and watching it go red. Several tests in this repo were caught passing on code that could not work.
- **Language: French for the product, English for the plumbing.** Routes (`/jeu`, `/connexion`, `/inscription`, `/salon`), domain modules (`etat.ts`, `coups.ts`, `partie.ts`, `plateau.ts`), their comments, the specs under `docs/superpowers/`, user-facing copy and **commit messages** are all French. The inherited starter layer (`lib/server/auth.ts`, `webhook/`, `outbox/`, `payments/`, this file) stays English. Match the file you are in rather than the repo average.
- Conventional Commits, French subject line — e.g. `feat(salon): expliquer chaque jeu sur son propre écran`.
- **Docs are under test.** [claude-md-shape.test.ts](src/lib/server/observability/claude-md-shape.test.ts) asserts this file's shape: no residue from the pre-port stack (the old framework's name, its old source paths, its middleware ordering) beyond the one historical negation in *What this project is*, and it must still mention cron + webhook + withdrawals + upload. Note the side effect: because the game format `EXPRESS` shares a name with that framework, write format names in their code casing here. `readme-shape.test.ts`, `env-shape.test.ts`, `vercel-json-shape.test.ts` and `runtime-enforcement.test.ts` do the same for their targets. Rewrite these docs freely — then run `pnpm test`.
- Node ≥ 20, pnpm ≥ 9 (see `engines` in [package.json](package.json)).
